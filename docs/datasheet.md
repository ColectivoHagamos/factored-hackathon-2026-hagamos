# Datasheet · demo subset

Status: draft, 2026-10-03. Built by `pipeline/demo.py`; counts in `docs/demo_subset_report.json`.

## 1. Purpose

The public demo of VERA needs realistic charges (amounts, dates, statuses, merchants and countries) so the legal clock, the sweep and the clarification steps can be shown end to end. The subset gives the demo that realism without exposing any identifier of the Factored dataset. It is not used to train or evaluate models.

## 2. Composition

| Item | Count |
|---|---|
| Customers | 47 (Argentina 14, Colombia 15, Mexico 18; basic 29, plus 11, premium 4, student 3) |
| Cards | 88 |
| Charges (purchases and bank adjustments) | 189, from the last 180 days up to the simulated clock (2026-06-18) |
| Dispute records | 8, from the last 365 days (needed for POL-08 and POL-17) |

## 3. Selection

Customers are chosen per acceptance scenario, three per scenario, plus two per segment. Among the customers that match a scenario, the order is given by a keyed hash, so the choice does not follow the source identifiers.

| Scenario | Criterion |
|---|---|
| A1 | Colombian customer, approved domestic purchase in the last 7 days, fraud score at most 30 |
| A2 | Pending purchase in the last 30 days |
| A3 | Card with two approved purchases in the last 14 days (the sweep) |
| A4 | Mexican customer, purchase in Madrid in the last 90 days |
| A5 | Argentine customer, credit card purchase in the last 30 days |
| A6 | Colombian customer, purchase in São Paulo in the last 60 days |
| A9 | Two approved purchases at the same merchant in the last 30 days |
| A10 | Approved bank adjustment in the last 60 days |
| Additional | Fraud score above 30, two or more disputes in 90 days, declined purchase, reversed purchase, known merchant |

Scenarios A7 (attack) and A8 (human request) depend on the conversation, not on the data, and use any of these customers.

## 4. Fields and origin

Origin: **F** = synthetic value of the Factored dataset; **P** = pseudonym (HMAC-SHA256); **G** = generated by the team; **D** = derived from F.

| Table | Field | Origin |
|---|---|---|
| customers | `customer_ref` | P |
| | `alias` (for example `CO-03 · plus`) | G |
| | `country_code`, `segment`, `customer_status` | F |
| | `age_band` | D (from the birth year) |
| | `scenarios` | G (selection criteria met) |
| cards | `card_ref`, `customer_ref` | P |
| | `masked_card` | G (invented last four digits) |
| | `card_type`, `status`, `expires_on` | F |
| charges | `charge_ref`, `customer_ref`, `card_ref` | P |
| | `kind`, `product_type`, `occurred_at`, `amount`, `currency`, `merchant`, `merchant_category`, `city`, `country_code`, `status` | F |
| | `amount_usd` | F, or D with the fixed dataset rate where the source is empty |
| | `fraud_score_band` (`<=30`, `>30`, `none`) | D |
| | `is_known_merchant` | D (approved purchase at the same merchant in the previous 365 days) |
| disputes | `dispute_ref`, `customer_ref` | P |
| | `created_at`, `subcategory` | F |

## 5. Removed

- Names, documents, emails, phone numbers, addresses and postal codes: removed in silver.
- Full card numbers: reduced to the last four digits in silver, then replaced by invented digits in the subset.
- The fraud label (`is_fraud`) and the raw fraud score.
- Free text: complaint descriptions and transcripts.
- Every other customer and every other table.

## 6. Pseudonymization

- Each identifier becomes `PREFIX-` plus the first 16 hexadecimal characters of HMAC-SHA256 over the kind and the value.
- The 256-bit key is created on first use, readable only by its owner, and stored outside the repository on the machine that builds the subset. It never reaches the repository, the CI or the server.
- The server receives the finished `demo.duckdb` and does not need the key, so nothing published can be traced back to an original identifier.
- **Pseudonymization is not anonymization:** with the key, the original identifier can be recomputed. That is why the key never leaves the building machine.
- Rotating the key changes every pseudonym.

## 7. Privacy test

- `auditar_cumplimiento.py --fuga-archivo demo.duckdb` cross-checks every candidate token of the subset against 26 million identifiers of the dataset: customer, product, transaction and complaint ids, documents, emails, phones and full names.
- A positive control proves that the check detects real identifiers in each of the 25 columns.
- Result on 2026-10-03: 25 of 25 columns detected by the control, and 0 real identifiers in the subset (356 tokens checked).
- The test runs again every time the subset is rebuilt; a non-zero result blocks the deployment.

## 8. Limitations

- The dataset is synthetic: amounts never exceed USD 500, Mexico operates only in USD, and the channel column is random, so VERA asks the customer whether the purchase was online.
- Complaints cannot be linked to their transaction in the source data; the subset keeps dispute records only to count them.
- The subset is small by design. It shows the flows; it does not measure them. Measurement uses the sealed evaluation set.

## 9. Distribution and maintenance

- `demo.duckdb` lives outside the repository and is copied once to the demo server, read-only.
- It is rebuilt with `make data`, which also rebuilds bronze, silver and gold, and its leak test is run again.
